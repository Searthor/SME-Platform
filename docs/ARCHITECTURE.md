# Architecture

## 1. Decision summary

The platform will be a TypeScript modular monolith in a pnpm workspace:

```text
Nuxt 4 web -> NestJS REST API -> PostgreSQL
                         |
                         +-> local/S3 storage adapter
                         +-> in-process events + transactional outbox
                         +-> later: Redis/BullMQ/workers/FCM
```

NestJS provides one deployable API with domain-oriented modules. Modules share one PostgreSQL database so critical sales, payment and inventory changes can commit atomically. Boundaries are enforced in code and ownership conventions so selected capabilities can be extracted later, but extraction is not an MVP goal.

## 2. Consequential decisions

| Decision | Current simplicity | Future path / trade-off |
| --- | --- | --- |
| Modular monolith | One deployment and local transaction | Enforced module APIs make extraction possible; weak boundary discipline would create a distributed monolith later |
| pnpm workspaces, no Nx/Turbo initially | Native scripts and low tooling overhead | Add a task runner only when build graph/caching becomes material |
| PostgreSQL + Prisma | Typed persistence and mature relational integrity | Raw SQL is permitted in repositories for locks/reporting; ORM must not dictate domain/API contracts |
| UUIDv7 IDs generated by application | Opaque, globally unique, time-local indexes | Requires a vetted generator; UUID column remains standard and migration-friendly |
| Product plus always-present variant | Simple products use a default variant | Variants can be exposed later without moving sales/stock foreign keys |
| Tenant column on all tenant data | Clear ownership and future RLS compatibility | More composite constraints; worth the protection and query locality |
| Balance plus immutable movement ledger | Fast availability checks and auditable history | Requires strict single writer and reconciliation tooling |
| Tenant-scoped repositories | Removes repeated unsafe filters | Some boilerplate; raw Prisma access is restricted to infrastructure repositories |
| Database row lock for stock writes | Correct and understandable under concurrency | Hot SKUs serialize; optimize only after measurement |
| Transactional outbox | Reliable post-commit side effects without Redis | Dispatcher can begin in-process and move to BullMQ later |
| Stable shared API contracts only | Prevents frontend coupling to persistence | Contract releases require deliberate compatibility management |

These choices—tenant ownership, IDs, product/variant identity, money precision/rounding, stock ledger semantics, auth session model and transaction boundaries—are expensive to retrofit and must be established before feature implementation.

Suggested backend module shape (use only layers the module needs):

```text
sales/

  application/     # commands, queries, orchestration, ports
  domain/          # entities/value objects/policies/events, no Nest/Prisma
  infrastructure/  # Prisma repositories and adapters

```

This is not a mandate to create four folders around trivial CRUD. Complex transaction domains (sales/inventory/purchases/payments) use the full shape; small reference modules may use controller/service/repository until complexity warrants more.

## 4. Dependency rules

1. HTTP controllers validate/map input and invoke one application use case. They contain no pricing, authorization, stock or persistence rules.
2. Domain code depends only on TypeScript and its own module concepts.
3. Application code may depend on domain types and ports, not Prisma or HTTP.
4. Infrastructure implements ports and may depend on Prisma/external SDKs.
5. Modules do not import another module's repositories or tables as an informal API.
6. Cross-module synchronous work uses a narrow exported application service/interface. Post-commit reactions use events.
7. Cycles are resolved by moving a capability to its rightful owner or defining a consumer-owned port—not `forwardRef` by default.
8. `core` contains technical capabilities; `common` must not become a miscellaneous business-logic bucket.

### Module ownership

| Module | Owns | Public collaborations |
| --- | --- | --- |
| Auth | credentials, refresh sessions, authentication methods | user identity lookup, token/session service |
| Users | global person profile and identities | user queries; no business role |
| Businesses | business profile/settings/timezone/currency | business context validation |
| Memberships | user-to-business membership and branch grants | active membership resolution |
| Access control | roles, permissions, role grants | permission evaluator/guard |
| Catalog | product, variant, category, unit, attributes/prices | sellable item snapshots |
| Inventory | warehouses, balances, movements, transfers | reserve/post/reverse stock operations |
| Sales | sale lifecycle/items/totals/history | invokes catalog, inventory and payments in transaction |
| Payments | generalized payment records/allocations/refunds | post/query payment for a payable reference |
| Purchases | purchase orders, receipts and totals | invokes inventory and payments |
| Reports | read-only reporting queries/projections | reads stable data; never changes transactions |
| Subscriptions | plans, entitlements, usage limits | centralized entitlement evaluator |
| Platform administration | global operator role, platform settings and platform audit | no implicit tenant repository or tenant-data access |

`categories`, `products`, and `units` may be Nest submodules inside the catalog bounded context. Warehouses, movements and transfers are similarly cohesive inside inventory. This avoids artificial network-shaped boundaries while preserving package-level organization.

## 5. Request execution

For an authenticated tenant endpoint:

1. Request-ID middleware accepts a valid correlation ID or generates one.
2. Authentication guard verifies access token claims and active session/user status as policy requires.
3. Business-context resolver verifies the requested active membership. The active business may be selected through a signed token claim plus server membership validation/cache; a client-supplied raw `businessId` is never authority.
4. Branch resolver validates the route/body branch against the business and member's branch grants.
5. Permission guard evaluates required permission and branch scope.
6. DTO validation/normalization runs with unknown fields rejected.
7. The application use case performs business validation and persistence through scoped repositories.
8. A response mapper returns the versioned API contract.

Tenant/request context is propagated with `AsyncLocalStorage` for logging and repository scope. Explicit context parameters remain acceptable in application interfaces and are required across job/event boundaries; hidden ambient context must not be the only source of authority.

Platform-administration endpoints use a separate deny-by-default `PlatformAdminGuard`. The authentication guard loads the current global role from the database-backed session/user relation on every request. A platform role never satisfies `TenantGuard`; accessing tenant-owned APIs still requires an active membership and scoped token.

## 6. Transaction strategy

Transactions are owned by application use cases, not controllers or individual repositories. A transaction manager passes a transaction-scoped unit of work/repository set. External calls are forbidden inside a database transaction.

Critical atomic boundaries include:

- complete sale: validate snapshots, sale/items, stock balances/movements, payments/allocations, status history, audit and outbox;
- cancel/refund: state transition, reversal payment/stock records, audit and outbox;
- purchase receipt: receipt lines, received quantities, balances/movements, status, audit and outbox;
- dispatch/receive transfer: transfer transition and relevant paired stock movements;
- permission change: grants, audit and session/authorization-version invalidation.

Use PostgreSQL's default `READ COMMITTED` plus explicit row locks/atomic conditional writes for inventory and other hot aggregates. Use `SERIALIZABLE` only for a narrowly measured invariant that cannot be expressed safely otherwise, with bounded retry on serialization failure. Lock multiple rows in deterministic ID order to reduce deadlocks.

## 7. Stock concurrency

The initial strategy is pessimistic row locking:

1. Resolve and validate all variant/location keys in the tenant.
2. Sort stock keys deterministically.
3. In one transaction, create missing balance rows safely, then select balance rows `FOR UPDATE` (raw SQL where Prisma does not expose the primitive).
4. Check availability while locked.
5. Apply decimal quantity deltas with a conditional non-negative invariant.
6. Insert one immutable movement for every delta.
7. Commit the containing business operation.

A database check enforces `quantity >= 0` while negative inventory is globally disabled. If per-business negative inventory is introduced, the unconditional check must be replaced by a safe policy-aware write strategy; a row cannot reference business settings in a simple check constraint.

Retries for deadlock/serialization errors are bounded and occur around the entire idempotent use case. Application-only prechecks are never relied upon. Balance-versus-ledger reconciliation runs as an operational check; it does not silently rewrite history.

## 8. Events and background work

Domain events describe facts in past tense and contain identifiers, tenant, occurrence time, event ID and schema version—not large mutable object graphs. In-process listeners may handle same-process, non-critical reactions. Required cross-transaction side effects use an `outbox_events` row written in the source transaction.

Initially an API-hosted dispatcher can claim outbox rows and invoke adapters with retry. Later, a dedicated worker and BullMQ/Redis can dispatch notification, export, file processing and analytics jobs without changing producers. Consumers must be idempotent. Jobs always carry `businessId`, actor/system identity, correlation ID and payload version.

Do not use events to split an invariant that belongs in one database transaction. `SaleCompleted` is emitted after the sale, stock and initial payment state are consistent.

## 9. Caching strategy

Start without distributed cache. In-process caches are allowed only for immutable/config-like data and must not be correctness dependencies. Add Redis for measured hot reads such as permissions, entitlements or reference data with tenant-prefixed keys and explicit invalidation/versioning. Never use cache as the authoritative stock, payment or idempotency store. Reports may later use TTL cache or materialized views; mutation services remain unaware.

- Nuxt pages coordinate route-level loading and compose domain components.
- Typed services own HTTP calls and contract mapping; page components do not construct ad-hoc endpoints.
- Composables own reusable UI workflows; Pinia holds durable client state such as authenticated user, active business/branch, POS cart and preferences.
- Server state is not duplicated globally without a reason. Sensitive authorization decisions are never inferred from hidden UI alone.
- Route middleware improves UX for authentication/context; the API remains authoritative.
- Money crosses the JSON boundary as decimal strings or minor-unit strings per contract, never JavaScript floating point.
- The client sends an idempotency key for critical commands and retains it across retries of the same intent.

## 11. Operational and security architecture

- Argon2id password hashing with configurable parameters; breached-password and account-throttling policy can be added.
- Short-lived JWT access token; opaque high-entropy rotating refresh token stored hashed in a session record.
- CORS allowlist, Helmet, request-size limits, route-specific rate limiting and secure cookies when refresh is web-cookie based.
- Structured JSON logs redact authorization, cookies, tokens, passwords and sensitive DTO fields.
- `/health/live` checks process health; `/health/ready` checks required dependencies without leaking details.
- Storage is behind a port. Local storage is development-only; S3-compatible production uses private objects and signed access.
- Uploads validate size, detected MIME, extension policy and ownership; database stores object key and metadata, not binary content.

## 12. Scalability path

1. **Initial:** Nuxt, one or more stateless NestJS instances, PostgreSQL, local development storage.
2. **Operational growth:** S3-compatible storage, Redis for measured cache/rate limits, BullMQ workers for outbox/jobs.
3. **Horizontal growth:** load balancer, multiple API/worker instances, managed PostgreSQL, connection pooling, read replicas for reporting where consistency permits.
4. **Data growth:** query optimization, materialized reporting views, archival/retention, then time partitioning of movements/audit/outbox if evidence supports it.
5. **Selective extraction:** notifications, file processing, external payment integrations or reporting are candidates. Sales and inventory remain together until a compelling consistency/ownership case exists.

RLS can be added as defense in depth because tenant tables carry `business_id`. Each transaction would `SET LOCAL app.business_id` and policies would compare it. Application scoping and tests remain mandatory.

## 13. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Cross-tenant data leak | Scoped repositories, composite tenant FKs, deny-by-default context, isolation tests, future RLS |
| Stock oversell | Row locking, non-negative constraint, atomic balance+movement, concurrency tests |
| Duplicate money/stock operation | Idempotency record and unique key scoped to business/operation; consumer deduplication |
| Decimal/rounding mismatch | Central money library, currency scale and documented rounding; strings at JSON boundary |
| Module boundary erosion | Public exports, architecture lint/review, no cross-module repository access |
| Auth revocation lag | Short access-token lifetime, session rotation/revocation, membership/authorization version checks |
| Reports overload primary DB | Bounded queries/indexes first, materialized views/cache/read replica later |
| Outbox/job poison message | Attempt limits, exponential backoff, dead-letter state and operator visibility |
| Audit contains secrets/PII | Field allow/deny lists, redaction, retention/access policy |
| Product scope expansion | Stable core capabilities, vertical modules and entitlements; roadmap gates |

## 14. Architecture decision records

Before implementation, create ADRs for at least: ID generation library, tax/rounding rules, stock costing, receipt numbering, refresh-token transport, Prisma multi-file schema support/version, and negative-inventory policy. An ADR records context, decision, alternatives, consequences and migration path; it does not replace these normative documents.
